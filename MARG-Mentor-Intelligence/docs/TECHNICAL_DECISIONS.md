## TD-01 Python 3.12 as the baseline — Accepted
- **Context:** the brief requires 3.12+. Both 3.12 and 3.14 are installed.
- **Decision:** `requires-python = ">=3.12"`. Development venv on 3.12 for the widest wheel compatibility (asyncpg, pydantic-core, etc.). CI should also run on the newest installed version.
- **Consequence:** no 3.13+-only syntax.

## TD-02 Modular monolith, FastAPI + async throughout — Accepted
- **Decision:** one codebase, two process types (API, worker). Async SQLAlchemy, async httpx, async Anthropic client.
- **Why:** simplest maintainable shape. Boundaries are enforced by package structure and interfaces, not network hops.

## TD-03 Dependency and project tooling: uv + pyproject.toml — Accepted
- **Decision:** `pyproject.toml` is the source of truth, `uv.lock` is committed, and `requirements.txt` is generated by `uv export` for environments without uv (the brief lists it as a deliverable).
- **Lint/format/type:** ruff + mypy (dev dependencies only).

## TD-04 Engine database: existing local PostgreSQL 18.6, portable models — Accepted (owner decision 2026-10-31)
- **Decision:** use the owner's existing PostgreSQL 18.6 service and the database `marg_mentor_intelligence` **only**. No second PostgreSQL instance is installed.
- **Access layer:** SQLAlchemy 2.x async + asyncpg + Alembic (async template).
- **Schema isolation:** application tables go in schema `mie` (`DB_SCHEMA`). PostgreSQL integration tests use schema `mie_test` (`DB_TEST_SCHEMA`) in the same database, created and dropped per test session. This keeps tests inside the approved database without polluting application data. The schema is selected through the connection's `search_path`, so models carry no hardcoded schema and also run on SQLite.
- **Dedicated login role:** `marg_mie_app`, which owns schemas `mie` and `mie_test` only. The owner creates it once (PHASE_1_PLAN §4). It is not a superuser and gets no grants on `marg_db`.
- **Credentials:** separate `DB_HOST/PORT/NAME/USER/PASSWORD` variables, combined in code with `sqlalchemy.URL.create()`. This avoids URL-encoding problems with special characters in passwords, and means a full DSN with password never appears in config or logs.
- **Unit tests:** SQLite in-memory (aiosqlite) with portable types (`Uuid`, `JSON`, timezone-aware `DateTime`), so they need no external services.
- **Compatibility note:** PostgreSQL 18 is newer than the versions asyncpg officially lists. Phase 1 verifies the connection, migrations and integration tests on 18.6 before relying on it. If a problem appears, the fallback is `psycopg` 3 (async), which affects only `app/db/`.
- This database belongs to the engine only. The engine has no MARG DB credentials.

## TD-05 Background jobs: ARQ (Redis), cron inside the worker — Proposed
- **Context:** the brief allows Celery or ARQ, plus APScheduler for scheduling.
- **Decision:** ARQ. It is asyncio-native (matches FastAPI and the async SDK), lightweight, and has built-in cron jobs, so **APScheduler is not needed** (one dependency fewer). Celery is less suitable here: it is sync-first, and its prefork pool is unsupported on Windows dev machines.
- **Risk:** ARQ's long-term maintenance status should be re-checked before Phase 5. Mitigation: business code depends on an internal `JobQueue` port, so swapping to Celery, SAQ or Taskiq touches only `app/jobs/`.
- **Durability:** the engine DB (event inbox, executions, dead letters) is the source of truth. Redis is transport only, so a lost Redis message is recoverable by a reconciliation job.
- **Windows risk:** ARQ installs OS signal handlers through asyncio, which the Windows event loop does not fully support. Running the ARQ worker natively on Windows must be verified in Phase 5. If it fails, the worker runs inside WSL2 next to Redis (see below), and the API stays on Windows.

### Redis on Windows: recommendation (owner decision pending)

**Docker is not necessary.** Redis is not needed until Phase 5. Phases 1–4 run with `REDIS_URL` empty, and readiness reports Redis as "not configured".

| Option | Pros | Cons |
|---|---|---|
| **A. Redis in WSL2 (Ubuntu) — recommended** | Official Redis on Linux, same as typical production. Free. Also gives a Linux host for the ARQ worker if native Windows fails. WSL2 forwards `localhost:6379` to Windows automatically. | One-time WSL2 setup (admin rights, reboot, virtualisation enabled in BIOS) |
| B. Memurai Developer (native Windows service) | Native Windows install, no WSL | Redis-*compatible*, not Redis. The free edition is for development only; check its licence terms. Doesn't help if the ARQ worker can't run natively. |
| C. Docker Desktop + Redis container | Matches container deployments | Heavy. Needs WSL2 anyway. Licence terms for larger organisations. Unnecessary for this project now. |

Redis has no official native Windows build. Old community ports (for example, Redis 3.x for Windows) are unmaintained and should not be used.

## TD-06 LLM provider abstraction — Accepted
- **Decision:** `providers/base.py` defines `LLMProvider` with `generate_structured(request: LLMRequest, schema: type[BaseModel]) -> LLMResponse[T]` and `generate_text(...)`. `LLMRequest` is vendor-neutral (system prompt id + version, messages, tier, max tokens, metadata). `AnthropicProvider` is the only implementation. `model_factory` maps tiers to configured models.
- **Consequence:** agents never import `anthropic`. Replacing Claude means adding one provider class.

## TD-07 Claude model selection: one configurable model — Accepted (owner decision 2026-10-31)
- **Decision:** a single model, set by `ANTHROPIC_MODEL`. **No model ID is hardcoded** in code, defaults or tests (tests use a placeholder such as `test-model`). Startup fails if `AI_ENABLED=true` and `ANTHROPIC_MODEL` is empty.
- **Future routing:** `providers/model_factory.py` exposes a `ModelRouter` interface. Phase 1 ships only `SingleModelRouter`. Agents pass a complexity hint (`light/standard/complex`) that is logged but ignored, so routing can later be added by configuration alone.
- **Owner's choice of model:** for reference (not used as a default), Anthropic's current recommended general model is `claude-opus-5-5`. Others include `claude-sonnet-5-5` and `claude-haiku-5-5`.
- **Effort:** `ANTHROPIC_EFFORT` is optional and sent only when set, because not every model supports every level.
- **Pricing is configuration only** (`LLM_PRICING`). If the configured model has no price entry, cost is reported as "not configured" and is never estimated.

## TD-08 Claude API usage rules — Accepted
Based on current Anthropic API behaviour for these models:
- **Official SDK** (`anthropic`, `AsyncAnthropic`). No raw HTTP, no OpenAI-compatible shims.
- **SDK version:** `anthropic` 1.x, which is built on `httpx2` (a maintained fork of httpx), not `httpx`. Consequence: SDK traffic cannot be mocked with `respx`. Tests inject a mock transport through the SDK's `DefaultAsyncHttpxClient` (TD-17). Exact SDK behaviour is verified against the version locked in Phase 1.
- **Credentials:** the provider passes the key from settings explicitly (`AsyncAnthropic(api_key=settings.anthropic_api_key.get_secret_value())`). It does not rely on the SDK's implicit credential discovery, so the startup validation is authoritative.
- **Structured output:** `client.messages.parse(..., output_format=<PydanticModel>)` → `response.parsed_output`, followed by our own re-validation and business checks. No assistant prefill (rejected by current models).
- **Thinking / effort:** the `thinking` parameter is omitted (current models default to adaptive thinking). Depth is controlled with the optional `ANTHROPIC_EFFORT` (TD-07).
- **No sampling params** (`temperature`/`top_p`/`top_k`). They are rejected on current models.
- **No forced `tool_choice`** (`any`/`tool` returns 400 on Opus 5.5 / Sonnet 5.5). The structured output path above makes it unnecessary.
- **Stop reasons:** always check `stop_reason` before reading content. Handle `refusal` (log category, deterministic fallback) and `max_tokens` (one retry with a higher limit, then fail).
- **Refusal fallback:** `ANTHROPIC_REFUSAL_FALLBACK=default` enables Anthropic's server-side fallback (beta `server-side-fallback-2026-07-01`, `fallbacks: "default"`), which reruns a policy-declined request on a suitable model. It is on in `.env.example` and only supported by some models on the Claude API, so set it to `off` for other models. Because the beta is used through the SDK's beta namespace, Phase 1 verifies that `client.beta.messages.parse` accepts it. If not, the fallback path uses `beta.messages.create` with `output_config.format` plus our own Pydantic validation. Every response records which model actually served it.
- **Errors:** catch typed SDK exceptions most-specific-first (`RateLimitError`, `APITimeoutError`, `APIConnectionError`, `InternalServerError`, `BadRequestError`, `AuthenticationError`, `PermissionDeniedError`). Only transient classes are retryable.
- **Retries:** use the SDK's built-in retry (honours `retry-after`, covers 408/409/429/5xx/connection) with `max_retries` and `timeout` from config. Job-level retry (ARQ, exponential backoff + jitter) handles longer outages. No retry on 4xx/validation.
- **Request IDs:** store the SDK's `_request_id` and our `execution_id`/`correlation_id` on each `llm_usage` row.

## TD-09 Prompt management and caching — Accepted
- **Prompts as versioned files** in `app/prompts/<agent>/<version>.md`, loaded by id + version. The version is recorded on every LLM call and execution.
- **Cache-friendly layout:** frozen system prompt (and any static schema/instructions) first with a `cache_control` breakpoint. Volatile data (dates, entity data) goes after it. Nothing time-varying in the system prompt. Verify with `usage.cache_read_input_tokens`.
- Short prompts below the model's minimum cacheable size will not cache, which is acceptable.

## TD-10 Cost controls — Accepted
- `needs_llm()` gate per agent. Events never call Claude by default.
- Daily planning makes one LLM call per mentor per day. Sub-agents contribute deterministic analysis only.
- Context minimisation: aggregates and IDs instead of raw records. Pseudonymised names.
- Per-mentor and global daily token budgets (config). When a budget is exceeded, results are deterministic-only and flagged as such.
- Duplicate-request protection: an LLM call is keyed by `hash(agent, prompt_version, model, minimised_context)` within a TTL. A hit reuses the stored result.
- `llm_usage` table: model, input/output/cache-read/cache-write tokens, computed cost (from configured prices), latency, prompt version. A `/usage` endpoint and the Phase 7 cost report are built from it.

## TD-11 Backend adapter and modes — Accepted
- `BACKEND_MODE=mock|marg`. Startup validation fails if `marg` lacks `MARG_BACKEND_BASE_URL` or auth settings, or if the dev principal header is enabled in `marg` mode.
- The endpoint registry is configuration-driven and **empty by default**. No paths are invented.
- No automatic mock fallback in any code path.
- httpx client: explicit connect/read timeouts, TLS verification on, bounded retries for idempotent GETs only.

## TD-12 Identity, permissions and isolation — Accepted as provisional (owner decision 2026-10-31)
- `Principal` (`user_ref`, `tenant_ref`, `roles`, `kind`) is propagated through every request and job. Repositories require `tenant_ref` + `mentor_ref`.
- **Engine permissions** (capabilities) are a code-level enum, because they describe what the engine can do.
- **Roles, tenant structure and the role → permission mapping are configuration** (`RBAC_CONFIG_PATH`, TOML, read with stdlib `tomllib`). The development file uses obviously placeholder role names (`dev_mentor`, `dev_supervisor`). **No final MARG roles are invented.** They will be defined from the MARG OpenAPI specification and compatibility audit.
- An unknown role gets no permissions (deny by default).
- Real authentication (likely MARG-issued token verification) is **deferred** to the backend audit. In mock mode a dev-only header principal is used, and it cannot be enabled when `BACKEND_MODE=marg`.

## TD-13 Approvals bound to payload hashes — Accepted
- An approval stores the SHA-256 of the canonical JSON of the proposal. Execution re-hashes and refuses on mismatch. Proposals have a TTL. Approver must be a human principal with the role mapped to that operation.

## TD-14 Idempotency strategy — Accepted
- Events: unique `event_id`. Derived events use UUIDv5 of a deterministic natural key.
- Jobs: ARQ `_job_id` = idempotency key.
- Tools: `tool_invocations.idempotency_key` unique. A repeat returns the stored result.
- Completion is recorded only after the side effect is confirmed.

## TD-15 Logging and observability — Accepted
- Standard-library `logging` with a JSON formatter (stdlib only, no structlog dependency initially). Context vars carry `execution_id`, `correlation_id`, `mentor_ref` (pseudonymised hash), and `request_id`.
- A redaction filter masks keys matching secret patterns and known PII fields.
- `/health/live` and `/health/ready` (DB, Redis, config validity; never secret values).
- OpenTelemetry is deferred until a target observability backend is known.

## TD-16 Time handling — Accepted
- Store UTC (`timestamptz`). Use `zoneinfo` for mentor-local rendering. An injectable clock in services makes deadline tests deterministic. The default timezone is `Asia/Kolkata` for development (owner decision 2026-10-31), configurable through `DEFAULT_TIMEZONE` and per-mentor preferences.
- On Windows, `zoneinfo` needs the `tzdata` package, so it is added as a dependency.

## TD-17 Testing approach — Accepted
- pytest + pytest-asyncio. `FakeLLMProvider` for all agent and orchestration tests. Anthropic provider tests inject a mock transport (`httpx2.MockTransport` through `DefaultAsyncHttpxClient`) that returns recorded-shape API responses and errors. **The test suite never calls the real Claude API.** An optional, manually run smoke test does, behind `RUN_LIVE_LLM_TESTS=1`.
- PostgreSQL integration tests are marked `postgres`. They run against schema `mie_test` and are skipped automatically when DB settings are absent.
- Categories: `tests/unit`, `tests/integration`, `tests/safety`, `tests/e2e`, with markers for tests that need PostgreSQL or Redis.

## TD-18 Protection of the MARG database — Accepted
- `DB_FORBIDDEN_NAMES` (default `marg_db,postgres,template0,template1`) is checked before any connection. A match aborts startup and Alembic.
- After connecting, the engine verifies `SELECT current_database()` equals `DB_NAME`, and that the active `search_path` schema equals `DB_SCHEMA` (or `DB_TEST_SCHEMA` in tests).
- Alembic's `env.py` applies the same guard and puts its version table in `DB_SCHEMA`.
- No code path, script or test references `marg_db`, except the forbidden-name list and the tests that prove the guard works.

## TD-19 Line endings — Accepted
- `.gitattributes` sets `* text=auto eol=lf`, with CRLF kept for `.bat`, `.cmd` and `.ps1` files. The repository and working tree use LF on every OS.

## TD-20 Prototype implementation decisions (31 Oct 2026) — Accepted (owner authorised implementation)
- Operational DEMO DATA is stored in engine tables and read through `DemoDataAdapter`, which implements the same adapter port the MARG adapter will use. `BACKEND_MODE=demo`; `marg` is refused.
- Structured output uses `messages.create` with `output_config.format` from `anthropic.transform_schema(<Pydantic model>)`. The stop reason is checked before parsing, then Pydantic validates. `messages.parse` was dropped because it raises before refusals can be detected.
- Anthropic SDK **2.3.0** (built on `httpx2`); provider tests use `httpx2.MockTransport`.
- Approvals: provisional supervisor roles via `DEV_SUPERVISOR_ROLES`; TOML RBAC deferred.
- Redis/ARQ deferred. Planning runs on request or via `POST /events`.
- Details and the status of every feature: [PROTOTYPE_STATUS.md](PROTOTYPE_STATUS.md).
